## 1. 프로젝트 정의 (개정)

### 1.1 한 문장

> 브루잉 커피 학습자가 자신의 장비와 원두를 입력하면 대회 검증 레시피를 자기 장비 기준으로 변환받아 실시간 가이드로 추출하고, 결과를 기록해 다음 잔을 개선하는 공개 브루잉 위키.

### 1.2 두 개의 역할

공개 사이트가 되면서 역할이 갈립니다. 이 구분이 전체 설계의 뼈대입니다.

**관리자 (나) — 위키를 쓰는 사람**
- 레시피 DB 큐레이션 (챔피언 레시피 구조화 + 해설 작성)
- 원두 DB 큐레이션 (내가 마셔본 원두를 기록·공개)
- 장비 카탈로그 관리
- 학습 노트 작성 (추출 이론, 용어집, 실험 기록)
- 방식: JSON 파일 직접 편집 + Git 커밋. 관리자 UI를 만들지 않습니다.

**방문자 — 위키를 쓰는 도구로 쓰는 사람**
- 자기 장비를 선택 (선택값은 브라우저에 저장 → 다음 방문 시 유지)
- 원두를 직접 입력하거나 공개 원두 DB에서 선택
- 추천받고 → 가이드로 추출하고 → 로그 남김
- 로그는 **본인 브라우저에만** 저장. 로그인 없음.

### 1.3 로그인을 만들지 않는 이유

공개 사이트인데 로그가 있으면 보통 회원가입을 붙이게 됩니다. 여기서는 의도적으로 안 합니다.

- 회원가입 장벽 = 방문자 대부분이 로그를 안 씀. 로그의 가치는 "쉽게 남길 수 있음"에서 나옴
- 서버·DB·인증·비밀번호 재설정·개인정보처리방침이 전부 따라옴. 커피 공부할 시간이 사라짐
- 대신: localStorage 저장 + **JSON 내보내기/불러오기 버튼**을 눈에 잘 띄는 곳에 둠
- 기기 간 동기화가 정말 필요해지면 그때 Supabase를 붙입니다 (6.2절)

## 2. 정보 구조 (모바일 기준)

모바일 우선이므로 하단 탭 바 4개 + 그 안의 스택 내비게이션 구조로 갑니다.

```
[ 하단 탭 ]
 ☕ 추출          🔍 탐색          📓 기록          📖 위키
  │                │                │                │
  ├ 원두·장비 입력  ├ 챔피언 레시피   ├ 로그 목록      ├ 추출 이론
  ├ 추천 결과      │  └ 상세         ├ 로그 상세      ├ 용어집
  ├ 추출 가이드    ├ 플레이버 탐색   ├ 다이얼인 그래프 ├ 실험 기록
  └ 테이스팅 입력  │  └ 원두 상세    └ 내보내기      └ 장비 도감
                  └ 원두 목록
```

**탭 배치 의도**
- 첫 탭이 `추출`인 이유: 가장 자주 쓰는 동작. 앱을 열 때 커피를 내리려고 여는 경우가 대부분
- `내 장비`는 별도 탭이 아니라 최초 1회 온보딩 + 설정에서 변경. 매번 물어보면 지칩니다

### 2.1 온보딩 (최초 방문 1회, 3화면)

```
1화면  어떤 드리퍼를 쓰세요?      → 인기 6종 큰 카드 + "더 보기"(전체 17종)
2화면  그라인더는요?              → 인기 8종 + "목록에 없어요"(직접 입력)
3화면  V60 기준 평소 세팅은?      → 그라인더 앵커값 프리필 + 사용자 조정
       (예: Timemore C3 → 20클릭)
```

3화면이 이 사이트의 핵심 장치입니다. 이유는 3.4절.

### 2.2 페이지 간 연결

- 원두 → 이 원두 추천 레시피 / 이 원두로 남긴 내 로그
- 레시피 → 내 로그 이력 / 어울리는 원두 / 내 변형
- 플레이버 노드 → 이 향미의 원두 / 이 향미를 내가 실제 감지한 로그
- 로그 → 이전 로그와의 파라미터 diff

### 3.4 Grinder — v0.1의 설계 결함 수정

**v0.1이 틀렸던 부분**

v0.1은 "분쇄도를 마이크론으로 정규화하면 그라인더 간 레시피 이식이 된다"고 했습니다. 실제로는 안 됩니다.

- 클릭당 마이크론은 제조사 스펙이거나 커뮤니티 추정치인데, 버 형상(코니컬 vs 플랫), 버 직경, 정렬 상태, 제로 포인트 잡는 방법이 전부 다릅니다
- 같은 "800µm"이 같은 입도 분포를 뜻하지 않습니다. 특히 플랫 버는 코니컬보다 균일도가 높아 같은 중위 입도에서도 추출이 더 강하게 나옵니다
- 실제로 Comandante와 1Zpresso의 마이크론 표기가 서로 맞지 않는다는 보고가 다수 있습니다

**v0.2의 해결: 앵커 + 상대 밴드 방식**

각 그라인더마다 **"V60 표준 세팅" 하나를 앵커(밴드 0)로 잡고**, 레시피는 마이크론이 아니라 앵커로부터의 밴드 오프셋으로 저장합니다.

```
밴드 스케일
 -3 매우 곱게(에스프레소~에어로프레스)
 -2 곱게
 -1 약간 곱게
  0 V60 표준  ← 앵커
 +1 약간 굵게
 +2 중간-굵게 (칼리타/중볶음)
 +3 굵게 (케멕스 근처)
 +4 매우 굵게 (콜드브루)
```

각 그라인더는 `step_per_band`(1밴드 이동 시 몇 클릭)를 가집니다.

| 그라인더 | 앵커 (밴드 0) | 1밴드 | 레시피 "+2" → 표시 |
|---|---|---|---|
| Comandante C40 | 25클릭 | 2클릭 | **27클릭** |
| Timemore C3 | 20클릭 | 2클릭 | **24클릭** |
| 1Zpresso J-Max | 90클릭 | 7클릭 | **104클릭 (3회전 +14)** |
| Fellow Ode Gen2 | 4번 | 1스텝 | **6번** |
| Baratza Encore | 20 | 2스텝 | **24** |
| 목록에 없음 | 사용자 입력 | 사용자 입력 | 계산 가능 |

**이 방식의 이점**
1. 목록에 없는 그라인더도 앵커만 입력하면 전부 지원됩니다. 카탈로그 완성도에 의존하지 않습니다
2. 사용자가 자기 앵커를 직접 조정할 수 있습니다. "내 C3는 22클릭이 표준"이면 그렇게 저장 → 이후 모든 레시피가 그 기준으로 보정
3. 부정확한 마이크론 숫자로 신뢰를 잃지 않습니다. 마이크론은 보조 참고값으로만 표시하고 "추정"을 명기

**카탈로그 21종 작성 완료** → `data/grinders.json`
핸드밀: Comandante C40 · 1Zpresso JX-Pro/J-Max/J-Ultra/K-Ultra/Q2 · Timemore C2/C3 · KINGrinder K4/K6 · Hario Skerton Pro · Kinu M47

### 3.5 Water — 정수 기준

정수를 기본값으로 두고 프리셋을 최소화합니다.

```jsonc
{
  "presets": [
    { "id": "filtered",  "name": "정수 (기본)",   "tds_ppm": [20, 60],  "note": "대체로 저미네랄. 챔피언 레시피의 저TDS 물과 성격이 가까움" },
    { "id": "tap",       "name": "수돗물",         "tds_ppm": [50, 150], "note": "염소 냄새가 향미를 덮을 수 있음" },
    { "id": "samdasoo",  "name": "삼다수",         "tds_ppm": [80, 120] },
    { "id": "volvic",    "name": "볼빅",           "tds_ppm": [110, 130] },
    { "id": "custom",    "name": "커스텀 미네랄",  "tds_ppm": null, "gh_ppm": null, "kh_ppm": null }
  ]
}
```

정수 사용자에게는 챔피언의 40ppm 저미네랄 물 조건에 대해 "정수로 근사 가능"이라고 안내합니다. 이 정도가 실용적인 수준이고, 물 레시피까지 파고드는 건 위키 문서(📖 탭)로 다룹니다.

### P4. 추출 가이드 (모바일 전용 설계)

```
┌──────────────────────────┐
│ ← 나가기        🔒 화면유지│
├──────────────────────────┤
│ 지난 메모                  │
│ "온도 88°C, 마지막 -20g"   │
├──────────────────────────┤
│                          │
│        0:42              │  ← 72pt, 한 화면 최대 요소
│    ▓▓▓▓▓▓▓░░░░  3/5      │
│                          │
│   ── 2차 푸어 ──          │
│                          │
│      120 g               │  ← 48pt 목표 누적
│                          │
│   20초 동안 · 스파이럴     │
│                          │
│   다음까지 8초             │
│                          │
├──────────────────────────┤
│  ⏸ 일시정지  │  다음 ▶    │  ← 엄지 도달 범위
└──────────────────────────┘
```

**모바일 설계 결정**
- 세로 고정. 회전 잠금
- Screen Wake Lock API로 화면 꺼짐 방지 (미지원 브라우저는 무음 비디오 폴백)
- 3초 전 카운트다운 진동(Vibration API) + 소리. **화면을 안 보고도 추출 가능**해야 함
- `다음 ▶` 수동 버튼 필수: 사람은 목표 무게 채우느라 늦어집니다. 실제 누른 시각을 `actual.step_times_s`로 기록
- 타이머는 `performance.now()` 기준. 백그라운드 진입 시에도 경과 시간이 어긋나지 않도록 절대 시각 기반으로 계산

**종료 → 테이스팅 입력 (마찰 최소화)**
```
필수 3개만:  종합 ●●●●○  ·  가장 두드러진 향미 [칩 선택]  ·  다음에 바꿀 것 [한 줄]
선택 (접힘): 산미/단맛/바디/후미/클래리티 슬라이더 · TDS · 사진
```

필수를 3개로 줄인 이유: 7항목 슬라이더를 다 채우게 하면 3일 뒤부터 아무도 기록하지 않습니다.

```
1단계   중앙에 대분류 9개만 원형 배치 (터치 타깃 충분)
        Fruity / Sour-Fermented / Green-Vegetative / Other
```

- PC(넓은 화면)에서는 3중 링 전체를 한 번에 렌더 (같은 데이터, 다른 뷰)

SCA Coffee Taster's Flavor Wheel은 **CC BY-NC-ND 4.0**입니다. NC(비상업)는 문제없지만 **ND(변형 금지)** 때문에 공식 이미지를 잘라 쓰거나 개조해 재배포하는 것은 허용되지 않습니다.

## 6. 기술 스택

### 6.1 권장 구성

```
coffee-wiki/
├─ index.html                 라우팅 + 셸
├─ app.js                     상태 관리 · 스코어링 엔진 · 타이머
├─ style.css                  모바일 퍼스트 (min-width 미디어쿼리로 PC 확장)
├─ data/
│   ├─ brewers.json           ✅ 작성 완료 (17종)
│   ├─ grinders.json          ✅ 작성 완료 (21종)
│   ├─ flavor-nodes.json      레벨 2까지 약 40개 → 레벨 3 확장
│   ├─ recipes.json           12~15개
│   ├─ beans.json             큐레이션
│   └─ water.json             프리셋 5개
└─ wiki/                      마크다운 문서 (추출 이론, 용어집)
```

**배포**: GitHub Pages 또는 Cloudflare Pages (무료, 정적, HTTPS 자동)
HTTPS가 필요한 이유: Screen Wake Lock, Vibration, 나중에 Web Bluetooth 저울 연동까지 전부 보안 컨텍스트를 요구합니다.

**왜 단일 HTML로 시작하는가**
- 이 프로젝트의 본질은 데이터 모델 + 스코어링 규칙이고, 그건 어느 스택으로 옮겨도 그대로 재사용됩니다
- 빌드 도구 없이 폰 브라우저에서 바로 확인 가능
- Git 커밋이 곧 배포. 관리자 UI를 만들 필요가 없습니다

### 6.2 다음 단계로 넘어갈 신호

| 신호 | 옮길 곳 |
|---|---|
| app.js가 2000줄 넘고 수정이 겁남 | Vite + React |
| 폰과 PC에서 같은 로그를 보고 싶다 | Supabase (익명 인증 또는 매직링크) |
| 방문자가 자기 원두를 등록·공유하고 싶어한다 | Supabase + 관리자 승인 큐 |
| SEO로 유입을 만들고 싶다 | Next.js SSG + Vercel |

지금은 1단계로 충분합니다. 처음부터 DB를 붙이면 인증·마이그레이션에 시간을 쓰고 정작 커피 공부는 못 합니다.

### 6.3 BLE 저울 연동 (Phase 4 후보)

Acaia · Timemore Black Mirror · Bookoo 같은 BLE 저울은 Web Bluetooth API로 실시간 무게를 읽을 수 있습니다. 이게 되면 P4 가이드가 시간 기준이 아니라 **무게 기준 자동 진행**으로 바뀌어 정확도가 크게 올라갑니다. Chrome 계열 + HTTPS 필요. 처음부터는 하지 않되, 6.1의 구조가 이걸 막지 않도록만 설계합니다.

### Phase 1 — MVP: 추천 + 가이드 + 로그 (3개 동시)
범위가 크므로 4단계로 나눕니다. 각 단계가 끝날 때마다 폰에서 실제로 써봅니다.

- **1a. 데이터 + 온보딩**
  - flavor-nodes 레벨 2, **표준 레시피 8개**(8.2절) + 챔피언 4개, water 프리셋
  - 온보딩 3화면 + localStorage 저장
  - 완료 조건: 폰에서 내 장비를 선택하고 저장한 뒤 새로고침해도 유지된다

- **1b. 추천 엔진**
  - 입력 아코디언 + 스코어링 + 근거 표시 + 변환 규칙
  - 완료 조건: 챔피언 레시피가 내 V60 + Timemore 세팅으로 변환돼 나온다

- **1c. 추출 가이드**
  - 상태 머신 + 타이머 + 진동/소리 + Wake Lock + 수동 다음 버튼
  - 완료 조건: 화면을 거의 안 보고 커피 한 잔을 끝까지 내릴 수 있다

- **1d. 로그**
  - 테이스팅 입력(필수 3개) + 저장 + 목록 + JSON 내보내기/불러오기
  - 완료 조건: 3일 연속 기록이 쌓이고, 파일로 백업했다가 되살릴 수 있다

**Phase 1 최종 완료 조건**: 아침에 폰으로 열어서 원두 입력 → 추천 → 추출 → 기록까지 한 번도 다른 앱을 켜지 않고 마친다

### Phase 2 — 챔피언 레시피 아카이브
레시피 12~15개 데이터화 · 목록/필터 · 상세 + 세로 타임라인 · 큐레이터 해설 작성

### Phase 3 — 플레이버 탐색
드릴다운 휠(레벨 2) · 원두 필터링 · 원두 상세 · 레벨 3 확장 · 표기 vs 내 감각 비교 모드

### Phase 4 — 분석 · 위키 · 확장
다이얼인 히스토리 그래프 · TDS×수율 차트 · 위키 문서 · BLE 저울 연동 검토

## 8. 시드 레시피 — 표준 레시피 세트

**v0.2 수정 사항**: 초안에서는 제작자 개인 레시피를 시드 1번으로 잡았는데, 이건 v0.1(개인 도구) 시절의 잔재입니다. 방문자가 자기 장비를 고르는 공개 사이트에서 제작자 개인 파라미터가 기준값이 될 이유가 없습니다. **널리 공개된 표준 레시피로 대체합니다.**

### 8.1 왜 "표준 레시피"가 필요한가

챔피언 레시피만으로는 사이트가 굴러가지 않습니다.

- 챔피언 레시피는 난이도 4~5, 특수 장비 전제(Melodrip, Solo Dripper, 저TDS 물)가 많습니다
- 입문자가 첫 화면에서 받을 추천이 난이도 5짜리면 이탈합니다
- 스코어링에 "난이도 적합" 항목이 있어도 **낮은 난이도 후보가 DB에 없으면 작동하지 않습니다**

즉 표준 레시피는 추천 엔진의 하한선을 채우는 역할입니다.

### 8.2 시드 목록 (Phase 1a 목표: 8개)

널리 공개돼 있고 출처가 명확하며 특수 장비가 필요 없는 것들로 구성합니다.

| # | 레시피 | 드리퍼 | 난이도 | 역할 |
|---|---|---|---|---|
| 1 | Hoffmann V60 (2회 푸어) | V60 | 2 | 가장 무난한 기본값. 라이트~미디엄 |
| 2 | Tetsu Kasuya 4:6 | V60 | 3 | 단맛/강도를 사용자가 조절하는 구조. 교육 가치 최상 |
| 3 | Kalita Wave 표준 (3회 푸어) | Kalita 185 | 1 | 플랫 베드 기준선. 입문자 기본값 |
| 4 | Rao/Perger 스타일 고교반 | V60 | 3 | 라이트 로스트 고수율 |
| 5 | Melitta 원팟 | Melitta 1x2 | 1 | 저가 장비 사용자 커버 |
| 6 | Hario Switch 하이브리드 | Switch | 2 | 침지+투과. 재현성 최상 |
| 7 | Clever 완전 침지 | Clever | 1 | 푸어 기술 배제. 원두 비교 실험용 |
| 8 | AeroPress 표준 | AeroPress | 1 | 별도 파라미터 체계 |

+ 챔피언 레시피 4~5개 (Phase 2에서 12~15개로 확장)

**커버리지 확인**: 이 8개로 카탈로그 17종 드리퍼 중 주요 geometry(cone / flat / immersion / hybrid / pressure)가 전부 커버되고, 난이도 1~3 구간이 채워집니다. 챔피언 레시피가 난이도 4~5를 맡습니다.

### 8.3 각 레시피에 반드시 붙는 것

파라미터만 옮겨오면 그건 그냥 남의 자료 정리입니다. 위키의 가치는 아래 두 필드에서 나옵니다.

- **`curator_commentary`** — "왜 이렇게 하는가"에 대한 직접 작성 해설
  예: 4:6 메소드의 앞 40%가 단맛/산미 균형을, 뒤 60%가 농도를 결정하는 구조인 이유
- **`coach_note`** (장비 카탈로그) — 이 장비로 이 레시피를 쓸 때 주의점

이 두 필드는 공부하면서 채워지는 것이지, 시작 전에 확정할 수 있는 게 아닙니다. **Phase 1a에서는 파라미터만 넣고 해설은 비워둔 채 시작해도 됩니다.**

### 8.4 개인 레시피는 어디로 가는가

없어지는 게 아니라 **방문자 기능**으로 흡수됩니다.

- 표준 레시피로 추출 → 로그에 결과 기록 → `next_action`으로 조정
- 조정이 반복되면 `my_variant_of`로 파생 레시피 저장 (원본과 연결)
- 이 흐름은 제작자에게도 똑같이 적용됩니다. 제작자는 별도 취급을 받지 않습니다

즉 제작자의 개인 레시피는 **기획 단계 입력값이 아니라 Phase 1d 사용 결과물**입니다. 이게 v0.2의 올바른 위치입니다.

### 8.5 Phase 0 잔여 작업

기획 확정에 남은 건 두 가지이고, 둘 다 외부 입력 없이 진행 가능합니다.

- [ ] `flavor-nodes.json` 레벨 2 작성 (약 40개) — WCR 용어 계층 정리 + 자체 색상 팔레트 정의
- [ ] `recipes.json` 시드 8개 구조화 — 파라미터만, 해설은 비움

두 작업이 끝나면 Phase 1a로 넘어갑니다.

## 9. 다국어 (한국어 / 영어)

### 9.1 왜 영어판이 자연스러운가

이 프로젝트는 원래 영어권 자료 위에 서 있습니다.

- 플레이버 휠 용어(Blueberry, Jasmine)는 영어가 원본이고 한글이 번역본입니다
- WBrC 챔피언 레시피, 장비명(Hario V60, Comandante C40)도 영어가 원본입니다
- 산지 표기(Ethiopia Guji Hambela)는 영어가 사실상 표준입니다

즉 **데이터의 상당 부분은 이미 영어입니다.** 번역해야 할 것은 UI 문자열과 제가 직접 쓰는 해설뿐입니다.

### 9.2 3개 층위로 나눠 접근

전부 번역하려 들면 프로젝트가 무너집니다. 층을 나눠 비용을 파악합니다.

| 층 | 대상 | 분량 | 비용 | 우선순위 |
|---|---|---|---|---|
| **L1. UI 문자열** | 버튼·라벨·안내 문구 | 약 200개 | 낮음 (1회) | P0 |
| **L2. 데이터 필드** | 원두명·산지·향미·장비명·프로세스 | 이미 대부분 영어 원본 | 낮음 | P0 |
| **L3. 서술형 콘텐츠** | `curator_commentary` · `coach_note` · 위키 문서 | 계속 증가 | **높음 (지속)** | P2 |

**L1 + L2만 끝내도 사이트 기능의 90%가 영어로 동작합니다.** 추천·변환·타이머·로그는 전부 숫자와 UI 문자열로 굴러가기 때문입니다.

### 9.3 L3에 대한 정책 — 이게 핵심 결정

해설을 두 언어로 쓰면 **글쓰기 부담이 2배**가 되고, 경험상 한쪽이 방치됩니다. 그리고 방치된 언어판은 사이트 전체의 신뢰를 깎습니다.

**정책: 폴백을 허용하고 그 사실을 표시한다.**

```
영어판에서 curator_commentary의 en이 없을 때

┌──────────────────────────────────┐
│ ⓘ Korean only                    │  ← 배지
│                                  │
│ (한국어 원문 그대로 표시)          │
│                                  │
│ [ Translate with browser ]       │  ← 브라우저 번역 안내
└──────────────────────────────────┘
```

- 번역이 전부 끝날 때까지 영어판 공개를 미루지 않습니다
- 어느 언어가 원본인지 `source_lang` 필드로 표기합니다
- 기계번역을 자동으로 채워 넣지 않습니다. 커피 용어에서 기계번역은 자주 틀리고, 틀린 해설은 없느니만 못합니다

### 9.4 스키마 개정 — 다국어 필드 구조

현재 `name_ko` / `name_en` 방식은 언어가 늘어날 때마다 필드가 증식합니다. **중첩 객체로 바꿉니다.**

```jsonc
// 이전 (v0.2)
{ "name_ko": "에티오피아 구지", "name_en": "Ethiopia Guji" }

// 개정 (v0.3)
{ "name": { "ko": "에티오피아 구지", "en": "Ethiopia Guji" } }
```

전체 적용 예:
```jsonc
{
  "id": "bean-001",
  "name":   { "ko": "에티오피아 구지 함벨라", "en": "Ethiopia Guji Hambela" },
  "roaster":{ "ko": "로스터명", "en": "Roaster Name" },

  "origin": {
    "country": "ET",                          // ISO 코드로 저장 → UI에서 로케일 변환
    "region":  { "ko": "구지", "en": "Guji" },
    "washing_station": "Hambela",             // 고유명사, 번역 안 함
    "altitude_m": [1900, 2100]
  },
  "variety": ["heirloom"],                    // 코드 → 표시명은 사전에서 조회
  "process": "natural",                       // 코드 → ko:"내추럴" / en:"Natural"
  "roast_level": "light",                     // 코드

  "flavor_nodes": ["fruity.berry.blueberry"], // 노드 id → 이름은 flavor-nodes.json에서

  "official_notes": { "ko": "…", "en": "…", "source_lang": "ko" },
  "curator_notes":  { "ko": "…", "en": null,  "source_lang": "ko" }  // ← 폴백 발생
}
```

**핵심 원칙: 열거형은 전부 코드로 저장하고 표시명은 사전에서 조회합니다.**
`process: "natural"` 하나만 저장하면 ko/en/향후 언어 표시가 사전 파일 한 곳에서 해결됩니다. 데이터에 한글을 직접 박으면 언어를 추가할 때 전체 데이터를 손봐야 합니다.

```jsonc
// data/i18n/terms.json
{
  "process": {
    "washed":  { "ko": "워시드",   "en": "Washed" },
    "natural": { "ko": "내추럴",   "en": "Natural" },
    "honey":   { "ko": "허니",     "en": "Honey" },
    "anaerobic": { "ko": "무산소 발효", "en": "Anaerobic" }
  },
  "roast_level": {
    "light":     { "ko": "라이트",      "en": "Light" },
    "full-city": { "ko": "풀시티",      "en": "Full City" }
  },
  "flow_rate": {
    "fast": { "ko": "빠름", "en": "Fast" },
    "slow": { "ko": "느림", "en": "Slow" }
  }
}
```

### 9.5 UI 문자열 파일

```
data/i18n/
├─ ko.json      UI 문자열 (한국어)
├─ en.json      UI 문자열 (영어)
└─ terms.json   열거형 사전 (공통, 언어별 값 포함)
```

```jsonc
// en.json 일부
{
  "brew.title": "Brew",
  "brew.next": "Next",
  "brew.pause": "Pause",
  "brew.resume": "Resume",
  "brew.exit": "Exit",
  "brew.keepScreen": "Keep screen on",
  "brew.step": "{current} / {total}",
  "brew.nextIn": "Next in {seconds}s",
  "brew.lastNote": "Last note",
  "rec.startThis": "Start this recipe",
  "rec.convertedFor": "Converted for your setup",
  "rec.needsConversion": "{from} → {to} conversion needed",
  "onboard.whichDripper": "Which dripper do you use?"
}
```

**규칙**
- 키는 `화면.요소` 형식. 평면 키를 씁니다 (중첩은 관리가 어려워집니다)
- 변수는 `{name}` 치환. 문장을 조각내어 이어붙이지 않습니다 — 어순이 다른 언어에서 깨집니다
  - 나쁨: `"다음까지 " + n + "초"` → 영어 어순에서 성립 안 함
  - 좋음: `t('brew.nextIn', {seconds: n})`
- 누락 키는 키 이름 그대로 노출합니다. 조용히 빈칸이 되면 발견이 늦습니다

### 9.6 언어 감지와 전환

```
최초 방문   navigator.language 확인
            'ko'로 시작 → 한국어 / 그 외 → 영어
이후        사용자 선택을 localStorage에 저장, 감지보다 우선
전환 위치   설정 화면 + 하단 위키 탭 상단 (본문이 긴 곳)
```

**URL 정책 (단계적)**

| 단계 | 방식 | 이유 |
|---|---|---|
| Phase 1 (단일 HTML) | `#/en/brew` 해시 라우팅 | 정적 파일 하나로 동작 |
| Phase 4 (SSG 전환 시) | `/en/brew` 경로 분리 | SEO. 검색엔진이 두 언어를 각각 색인 |

경로 분리로 갈 때 `<link rel="alternate" hreflang="ko|en|x-default">`를 추가합니다. 이게 없으면 검색엔진이 두 언어판을 중복 콘텐츠로 볼 수 있습니다.

### 9.7 단위는 언어와 분리한다

영어 = 미국이 아닙니다. 그리고 스페셜티 커피 씬은 국제적으로 °C와 g를 씁니다.

- **언어 설정과 단위 설정을 분리합니다.** 영어판 기본도 °C / g
- 화씨 토글은 별도 옵션으로 제공 (미국 사용자 대응)
- 무게는 g 고정. oz 변환은 하지 않습니다 — 커피 저울이 전부 g 단위입니다

| 항목 | ko | en |
|---|---|---|
| 온도 | 94 °C | 94 °C (설정 시 201 °F) |
| 무게 | 240 g | 240 g |
| 시간 | 3:28 | 3:28 |
| 날짜 | 8/14 | Aug 14 |
| 비율 | 1:16 | 1:16 |
| 분쇄 | 24 클릭 | 24 clicks |

### 9.8 작업 순서

Phase 1a에 L1·L2를 넣습니다. 나중에 붙이면 하드코딩된 한글 문자열을 전부 찾아내야 합니다.

- **1a에 포함**: `ko.json` / `en.json` / `terms.json` 구조 + `t()` 함수 + 언어 토글
- **1a 이후**: 새 문자열은 처음부터 키로 추가. 한글을 코드에 직접 쓰지 않는 규칙을 지킴
- **Phase 2 이후**: `curator_commentary`를 한국어로 먼저 쓰고 영어는 여유 될 때. 폴백 배지로 정직하게 표시

> 다국어를 "나중에 붙이는 기능"으로 두면 거의 반드시 실패합니다. 구조만 처음에 잡아두면 번역은 언제든 채울 수 있습니다.
